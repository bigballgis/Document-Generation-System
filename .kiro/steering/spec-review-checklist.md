# Spec 审查方法论

## 修复-再审查循环 (Fix-Then-Reread)

1. 每轮重新读取完整文档 (不依赖记忆)
2. 按当轮维度逐项检查
3. 逐个修复 (不批量延后)
4. 修复后重新读取确认无回归
5. 确认后进入下一轮

禁止: 批量修复、跳过重读、混合多维度。

## 多文档交叉验证

- 每个事实至少两个文档一致
- 需求 AC → 设计实现描述 → 任务对应项
- 文件路径、组件名、API 端点、i18n key 三文档一致

## 五轮审查维度

1. 结构完整性: 章节齐全、编号连续、无可选标记
2. 跨文档一致性: AC↔设计↔任务引用正确、路径/名称一致
3. 代码级验证: Java 方法签名、ErrorCode 存在性、DTO 字段、TS 类型匹配
4. 边界条件: 空数据/API 失败/并发防护/部分成功/大数据量/未保存变更/null 处理
5. 实现可行性: 时序竞态、组件生命周期、向后兼容、N+1 调用、私有方法复用、文件名安全

## 常见回归

- 引用断裂: 改编号/组件名/i18n key 后其他文档未同步
- 逻辑矛盾: 修复数据流后下游假设失效
- 遗漏传播: 新增 AC/组件/状态后其他文档未同步

## 优先级

P0=阻塞实现 (签名/类型/路径错误), P1=功能缺陷, P2=体验问题, P3=代码质量

## 停止条件

连续两轮无问题，或最后一轮仅 P2/P3，或已完成全部 5 维度。
