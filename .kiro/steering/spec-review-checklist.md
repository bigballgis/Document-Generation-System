# Spec 文档多轮深度审查方法论

## 核心原则

### 修复-再审查循环（Fix-Then-Reread）

每轮审查必须遵循严格的循环流程：

1. **完整读取** — 每轮开始时重新读取所有待审查文档的完整内容（不依赖上一轮的记忆）
2. **发现问题** — 按当轮审查维度逐项检查，记录所有发现
3. **逐个修复** — 对每个问题立即修复（不批量延后）
4. **重新读取修复后的文档** — 修复可能引入新问题（拼写错误、引用断裂、逻辑矛盾），必须重新读取确认
5. **确认无回归** — 确认修复未破坏其他部分后，才进入下一轮

禁止行为：
- 禁止在一轮中发现所有问题后批量修复（修复 A 可能影响 B 的上下文）
- 禁止跳过重新读取步骤（"我刚改的，肯定没问题"是最常见的回归来源）
- 禁止在同一轮中混合多个审查维度（焦点分散导致遗漏）

### 多文档交叉验证（Cross-Document Triangulation）

当审查涉及多个关联文档（requirements.md、design.md、tasks.md）时：
- 每个事实必须在至少两个文档中一致（三角验证）
- 需求中的每个 AC 必须能在设计文档中找到对应实现描述
- 设计文档中的每个组件/接口必须能在任务文档中找到对应任务
- 任务文档中的每个 `_Requirements` 引用必须在需求文档中存在且语义匹配

### 逐层深入（Progressive Depth）

每轮审查选择不同的审查维度，从宏观到微观逐层深入：
- 第 1 轮：结构完整性（文档结构、章节覆盖、编号连续性）
- 第 2 轮：跨文档一致性（三文档交叉验证、引用正确性）
- 第 3 轮：代码级验证（API 签名、类型定义、组件 props 与实际代码匹配）
- 第 4 轮：边界条件与异常场景（空数据、失败降级、并发防护、部分成功）
- 第 5 轮：实现可行性与破坏性测试（时序竞态、性能瓶颈、向后兼容）

## 审查维度详细清单

### 维度 1：结构完整性
- 需求文档：Introduction、Glossary、Requirements 章节齐全
- 每个 Requirement 有 User Story + 追溯 + AC 列表
- AC 编号连续无跳跃（1, 2, 3... 不是 1, 2, 4）
- 设计文档：Overview、Architecture、Components、Data Models、Correctness Properties、Error Handling、Testing Strategy 章节齐全
- 任务文档：Overview、Tasks、Notes 章节齐全
- 所有任务无 `*` 可选标记（用户要求全部必需）

### 维度 2：跨文档一致性
- 需求 AC → 设计组件/接口：每个 AC 有对应实现
- 设计组件 → 任务子任务：每个组件有对应创建任务
- 任务 `_Requirements` → 需求 AC 编号：引用存在且语义匹配
- 文件路径三文档一致（组件路径、API 文件路径、测试文件路径）
- 组件名、prop 名、emit 事件名三文档一致
- API 端点路径、HTTP 方法、参数名三文档一致
- i18n key 前缀和命名三文档一致

### 维度 3：代码级验证（需读取实际代码文件）
- 后端 Java 方法签名（参数数量、类型、返回值）与设计文档匹配
- ErrorCode 常量在 ErrorCode.java 中存在
- DTO 字段在对应 DTO 类中存在（特别注意 updatedAt vs createdAt）
- 前端组件 props/emits 定义与设计文档中的使用方式匹配
- API 函数签名（参数类型、返回类型）与 api/*.ts 中的定义匹配
- TypeScript 类型/接口字段与 types/*.ts 中的定义匹配
- Composable 返回值与实际 composable 文件匹配
- Store 扩展与现有 store 结构兼容

### 维度 4：边界条件与异常场景
- 空数据场景（0 条记录）有对应的空状态 UI 和 i18n key
- API 失败场景有对应的错误处理（ElMessage.error / 降级显示 / 重试按钮）
- 并发操作防护（双击删除 → 按钮禁用、快速切换标签 → 状态守卫）
- 部分成功场景（如创建成功但保存失败）有降级处理和用户提示
- 大数据量场景（50+ 片段、分页 API）有分页或虚拟滚动考虑
- 未保存变更场景有确认对话框守卫（标签切换 + 路由离开）
- 浮点数比较使用 >= 而非 ===（如覆盖率 100%）
- 可选字段的 null/undefined 处理（如 lockedVersion、dataScope）

### 维度 5：实现可行性与破坏性测试
- 状态同步时序：watch vs onMounted、Promise.all 完成顺序、deserialize 调用时机
- 组件生命周期：el-tabs 是否销毁非活跃 tab pane、onMounted 是否重复触发
- 向后兼容：后端参数从 required 改为 optional 是否破坏现有调用方
- 性能：N+1 API 调用（如逐个检查锁状态）是否需要并行化
- 私有方法复用：跨 Service 调用 private 方法不可行，需复制或提取工具类
- 文件名安全：用户输入的名称用于文件路径时需清理特殊字符

## 常见回归模式（修复引入的问题）

### 引用断裂
- 修改需求 AC 编号后，设计文档和任务文档中的引用未同步更新
- 修改组件名后，其他文档中的引用未更新
- 修改 i18n key 名后，模板代码中的引用未更新

### 逻辑矛盾
- 修复 A 处的数据流后，B 处依赖 A 的旧数据流产生矛盾
- 修复 store 初始化逻辑后，组件中的 watch/onMounted 假设不再成立
- 修复 API 参数后，前端调用代码中的参数传递不匹配

### 遗漏传播
- 在需求中新增 AC 后，设计文档和任务文档未同步新增对应内容
- 在设计中新增组件后，任务文档未新增对应创建任务
- 在 store 中新增状态后，$reset 方法未清理新状态

## 审查效率优化

### 优先级排序
- P0（阻塞实现）：API 签名不匹配、类型定义错误、文件路径错误
- P1（功能缺陷）：缺少错误处理、缺少空状态、缺少边界条件处理
- P2（体验问题）：i18n key 遗漏、UX 细节不一致
- P3（代码质量）：命名不规范、注释缺失

### 何时停止审查
- 连续两轮审查未发现任何问题 → 可以停止
- 最后一轮仅发现 P2/P3 级别问题 → 可以停止（在实现阶段修复）
- 已完成所有 5 个维度的审查 → 可以停止
